## 宿主命令行原型 v0.1.3

**当前目标**：作为普通 Rust 程序在 Windows/Linux 终端运行，逐步实现操作系统模块。当前不是独立内核，也不是 OS 级安全沙箱。

### 运行方式

在项目目录执行：

```powershell
cargo run
```

Cargo 在项目 `target` 目录构建；程序启动后读取 `.env`，再初始化或校验虚拟根目录。虚拟根不存在时也能构建，运行时由 Rust 创建它。命令说明见[初始化后命令与模块开发对照](docs/ubuntu-style-commands.md)。

### 初始化与数据边界

当前 `.env`：

```dotenv
ELARA_DATA_ROOT=D:/os
```

M 盘在当前机器上不存在；`D:/os` 是此前新建的专用目录，没有映射盘符或修改分区。

Rust 初始化允许创建新目录或接管空目录；拒绝接管无项目标记的非空目录。已标记目录只补缺失目录，不覆盖已有文件。目录布局包括 Ubuntu 风格的 `root/tmp/usr/etc/var/home/boot/dev/proc/sys` 等，完整清单以 `src/config.rs` 中的 `ROOTFS_DEFAULTS` 为准。

- 运行时写入只用于配置的数据根及其初始化目录、标记。`.env` 是项目中的必要只读输入。
- `proc/sys/dev` 是项目数据目录，不挂载或映射宿主资源；`snap` 目录不表示实现了 Snap。
- `bin/lib/sbin` 为普通目录，不照搬宿主软链接。
- 不创建 `swapfile`、`lost+found` 或 `*.usr-is-merged`。
- 拒绝越界路径、宿主盘符路径、Windows 设备名、alternate data stream、符号链接与 reparse point。
- 不执行宿主命令，不改启动配置、注册表、服务、驱动、分区，不建立网络连接。
- **目录与能力句柄约束不等于 OS 级安全隔离**：路径替换保护、系统只读与事务恢复由文件系统模块实施；宿主原型仍不能限制恶意修改后的程序或宿主其他进程，不声称是完整 OS 安全沙箱。
- 运行时数据根与构建工具行为分开：Cargo 只负责项目 `target` 构建，不读取 `.env`；虚拟根只由运行中的 Rust 程序初始化。
- 项目中的旧 exe、空目录、过期测试夹具和零散 txt 已清理；`target/repair-backups/` 保留 Cargo 配置备份。

## 1. 完整操作系统的边界

**完整操作系统不只是内核，而是“启动链路 + 内核 + 驱动 + 系统服务 + 用户环境 + 安装维护体系”。**

Linux 严格说是内核；一个 Linux 发行版把这些东西组合起来，才形成用户能安装、运行、维护的完整系统。嵌入式系统可以裁掉很多模块，桌面系统则通常需要更全面的功能。

这些是功能划分，不是固定的代码部署位置。宏内核通常把较多功能放在内核态；微内核可以将文件系统、驱动等放到用户态，通过 IPC 协作。

UEFI / BIOS 通常属于机器固件，不是必须自行实现的 OS 模块。GUI、动态链接器、包管理器也不是所有操作系统成立的必要条件。

## 2. 启动层：把机器带进操作系统

| 模块 | 负责什么 |
|---|---|
| 引导程序 bootloader | 加载内核，传递内存布局、启动参数等信息 |
| 内核入口与早期初始化 | 建立栈、准备 CPU 状态、初始化最早可用的日志输出 |
| 硬件发现 | 获取 CPU、内存、总线和设备信息，例如 ACPI、设备树 |
| 初始根文件系统 | 在正式磁盘和文件系统可用之前，提供必要的启动文件；不是所有系统都需要 |

可以利用现有固件和 bootloader，不必从机器通电后的第一条指令全部重写。

## 3. 内核层：管理资源、隔离程序

### 3.1 CPU 与中断管理

- CPU 初始化、特权级配置。
- 异常处理：缺页、非法指令、除零等。
- 硬件中断分发。
- 定时器。
- 多核启动、核间中断。

它负责回答：**CPU 遇到异常或设备发来信号时，该怎么处理？**

### 3.2 内存管理

| 子模块 | 作用 |
|---|---|
| 物理内存分配 | 管理实际 RAM 中哪些页空闲、哪些页已占用 |
| 虚拟内存与页表 | 将程序地址映射到物理内存，并控制访问权限 |
| 内核内存分配器 | 给内核对象分配内存 |
| 进程地址空间 | 隔离不同程序的代码与数据 |
| 内存映射 | 映射文件、共享内存、设备内存 |
| 内存压力处理 | 回收缓存、选择是否换页、处理内存不足 |

**“有个堆分配器”不等于“完成了内存管理”。** 进程隔离、缺页处理和回收策略往往更复杂。

换页并非必需功能，但内存耗尽时如何处理必须有明确策略。

### 3.3 进程、线程与调度

- 创建、退出、等待进程。
- 创建与管理线程。
- 保存和恢复执行上下文。
- 选择下一条运行的线程。
- 抢占、优先级、时间片。
- 多核负载分配与 CPU 亲和性。
- 阻塞、唤醒和等待队列。

它负责回答：**谁在什么时候使用哪一个 CPU？**

### 3.4 同步与进程间通信

- 原子操作、锁、信号量。
- 管道、消息队列。
- 共享内存。
- 本地 socket 或其他 IPC。
- 事件通知、信号或类似机制。

**调度解决“谁运行”，同步解决“如何不冲突”，IPC 解决“如何交换信息”。** 这三块关联很紧，但不是一回事。

### 3.5 系统调用与程序接口

用户程序不能直接随意操作硬件，需要受控入口：

- 打开、读写、关闭文件。
- 创建线程或进程。
- 分配、映射内存。
- 等待事件。
- 网络通信。
- 查询时间。

还要规定 **ABI**：参数怎么传、返回值怎么表示、寄存器如何使用、数据结构如何布局。

不一定要兼容 POSIX，但必须有自己的明确契约。

### 3.6 安全与资源控制

- 用户、身份、权限。
- 文件和设备访问控制。
- 用户态 / 内核态隔离。
- 系统调用参数校验。
- 资源配额、限制与记账。
- 随机数与必要的密码学基础设施。
- 沙箱、审计等扩展机制。

**安全不只是登录时检查密码。** 每一次跨越权限边界，都需要正确检查。

## 4. I/O 层：让软件真正使用硬件

### 4.1 设备与驱动框架

不只是写几个驱动，还要有统一的设备生命周期：

- 总线枚举与设备匹配。
- 驱动加载、初始化、卸载。
- 中断处理。
- DMA 与设备缓冲区管理。
- 热插拔、错误恢复。
- 设备资源与电源状态管理。

具体驱动包括：

| 类别 | 例子 |
|---|---|
| 基础设备 | 串口、定时器、中断控制器 |
| 存储 | NVMe、SATA、VirtIO block |
| 网络 | 网卡、VirtIO net |
| 输入 | 键盘、鼠标、触摸设备 |
| 显示 | framebuffer、GPU |
| 其他 | USB、音频、传感器 |

**真实硬件兼容性，是完整 OS 工作量的大头之一。** QEMU 中支持一种虚拟设备，与支持大量真实机器，差距很大。

驱动不一定支持动态加载；功能裁剪应明确，而不是将未实现功能默认为可用。

### 4.2 存储与文件系统

从下往上通常包括：

1. **块设备层**：读取和写入磁盘块。
2. **I/O 队列与缓存**：组织请求、缓存数据、控制写回。
3. **分区与卷管理**：识别分区，可能支持逻辑卷、加密卷。
4. **具体文件系统**：管理文件、目录、元数据和空闲空间。
5. **VFS 或类似抽象**：向应用提供统一接口。
6. **一致性与恢复**：处理掉电、写入中断、损坏检测。

存储引擎开发经验在这里很有用，但 **KV 引擎不直接等于文件系统**。文件系统还需要目录、文件偏移、权限、链接、挂载、打开句柄等语义；具体支持范围取决于系统设计。

### 4.3 网络子系统

- 网卡收发接口。
- 链路层、地址解析。
- IP、路由。
- TCP / UDP 等传输协议。
- socket 接口。
- 缓冲、拥塞控制、超时与重传。

DNS、DHCP、TLS 等功能常由用户态库或服务承担，**不必全部塞进内核**。

### 4.4 时间与电源管理

- 单调时钟、墙上时间。
- 定时器与超时。
- 休眠、唤醒。
- 关机、重启。
- CPU 空闲状态与频率控制。
- 电池、温度和相关设备管理。

这里尤其要区分：**测量经过了多久的时钟，不能随意使用会被校时修改的日历时间。**

## 5. 用户态：让系统能被使用

内核能运行用户程序后，还需要这些：

| 模块 | 负责什么 |
|---|---|
| 可执行文件加载 | 装载程序、建立初始地址空间和栈；可能由内核与用户态共同完成 |
| 运行库 | 为应用包装系统调用，提供常用基础功能 |
| 动态链接器 | 加载共享库、处理符号；全静态系统可以不需要 |
| 初始进程 / 服务管理器 | 启动服务、回收退出进程、管理服务生命周期；具体职责可拆分 |
| shell 与基础工具 | 执行命令、管理文件、查看进程和设备 |
| 系统服务 | 日志、网络配置、身份认证、时间同步等 |
| 图形环境 | 显示服务、合成器、窗口管理、输入处理 |
| 用户应用 | 编辑器、浏览器、终端等 |

**GUI 不是操作系统成立的必要条件。** 无图形界面的服务器或嵌入式系统，同样可以是完整系统。

## 6. 交付与维护：让系统不止在作者机器上能跑

这部分容易被忽略，但决定它能否长期使用：

- **构建体系**：交叉编译、链接、生成启动镜像。
- **安装与部署**：把系统装到设备上，配置启动方式。
- **更新与回滚**：更新失败后还能恢复。
- **配置与软件管理**：维护系统配置、依赖和应用。
- **诊断体系**：日志、崩溃信息、调试器、性能分析。
- **测试体系**：单元测试、虚拟机测试、真实硬件测试、故障注入。
- **恢复环境**：系统无法正常启动时，还能检查和修复。

“包管理器”不是所有 OS 都必须有，但 **系统软件如何交付和更新** 总得有答案。

## 7. 一次文件读取的模块协作

以应用读取一个普通文件为例，下面展示一种常见的缓存读取路径，并非所有 OS 或所有 I/O 模式的唯一实现：

```text
应用调用 read
    ↓
运行库进入系统调用
    ↓
内核检查句柄、权限和用户缓冲区
    ↓
文件系统定位文件数据
    ↓
数据在缓存中？
    ├─ 在：直接返回
    └─ 不在：提交磁盘读取请求
                 ↓
             驱动操作设备
                 ↓
             当前线程阻塞，调度其他线程
                 ↓
             设备完成，触发中断或被轮询发现
                 ↓
             唤醒等待线程
                 ↓
             数据交给应用，返回读取结果
```

**一个普通的文件读取，就可能穿过系统调用、权限、内存、文件系统、缓存、驱动、中断和调度。** 难的不只是分别写出这些模块，而是让它们在并发、错误和资源不足时仍然配合正确。

## 8. Rust 实现边界与建议开发顺序

### 8.1 Rust 能承担什么

Rust 可以用于内核、驱动和用户态组件。裸机内核通常使用 `#![no_std]`，并自行提供启动入口；`#![no_main]` 常用于禁用默认的程序入口安排。

**Rust 不会让底层硬件操作自动安全。** 页表、寄存器、MMIO、上下文切换等部分仍需要 `unsafe` 和少量汇编。重点是把它们封装成边界清楚、约束可验证的接口，而不是到处散落 `unsafe`。

### 8.2 建议的第一条开发主线

建议先以 **x86_64 + QEMU + 现成 bootloader** 为起点。这是起步建议，尚未确定具体依赖、版本或工具链。

逐步推进：

1. **启动**：内核能被加载并输出串口日志。
2. **异常与中断**：可控触发异常并处理，定时器中断可观测。
3. **内存管理**：物理页、页表、内核堆逐步可用。
4. **内核线程**：能够切换线程，并验证阻塞与唤醒。
5. **用户态隔离**：运行用户程序，并验证越权访问被阻止。
6. **系统调用**：用户程序通过明确的 ABI 请求内核服务。
7. **文件系统**：先明确存储介质与一致性目标，再实现文件读写。
8. **shell**：能够从命令环境启动用户程序，形成基本使用闭环。

这条线跑通，得到的是一个有实际功能的基础 OS。再补网络、真实硬件驱动、维护体系和长期稳定性，才逐渐走向可日常使用的系统。

**教学内核与能够替代 Linux 的通用操作系统，是两个量级。** 不应把“能启动”或“模块代码已写完”当作完整系统已经交付。
