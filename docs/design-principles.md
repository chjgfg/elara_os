# ElaraOS 设计原则：无垃圾与流畅

> 规定系统如何从源头避免积累垃圾、保持响应，而不是事后清理。其他会话实现任何写入、任务或资源相关功能前必须先读本文件。

## 1. 文档信息与权威入口

- **建立日期**：2026-11-07。
- **来源**：用户要求把 macOS "流畅的真实来源"（内存压力策略、QoS 调度、固定节拍、不积累垃圾）纳入 ElaraOS，并明确拒绝 Windows 式注册表、服务面板、驱动管理器等分散管理面。
- **适用阶段**：ElaraOS 是命令行系统，没有图形页面；本文只写命令行系统能落地的形式。涉及独立内核的部分标注"内核阶段"，宿主原型阶段只做数据结构和文件系统规则。
- **权威关系**：[README](../README.md) 管理项目状态；[模块总览](operating-system-modules.md) 解释模块职责；[命令账本](ubuntu-style-commands.md) 管理命令语义；本文管理**跨模块的设计约束**，模块实现与本文冲突时以本文为准，除非本文被修订。

## 2. 核心判断

**Windows 需要清理垃圾，是因为任何程序可以往任何地方写、写完不登记。** 垃圾之所以"隐形"，是因为系统不知道那是谁写的、为什么写、什么时候可以删。

**macOS 不需要清理垃圾，是因为它不允许无主写入。** 系统目录只读，应用只能写自己的沙箱，缓存由系统统一管理并可随时清空，临时文件有明确生命周期。

因此 ElaraOS 的规则只有一条根原则，其余都是它的推论：

> **每一个字节写入磁盘时，系统都必须知道它属于谁、属于哪一类、什么条件下可以删除。不满足这三点的写入被拒绝。**

一个系统如果需要"清理工具"，说明它违反了这条原则。ElaraOS 不提供清理工具；出现需要清理的东西时，修写入源头。

## 3. 七条原则

### P1 系统目录只读

| 项目 | 内容 |
|---|---|
| 规则 | `/bin`、`/sbin`、`/lib`、`/usr`、`/boot` 及其子目录在运行时对所有命令只读，包括将来的 root 身份。只有更新事务（P6）能改它们。 |
| 禁止的事 | 应用把自己的文件、配置、缓存写进系统目录；用户在系统目录下 `touch`、`mkdir`。 |
| 允许写入的根目录 | `/home`、`/root`、`/tmp`、`/var`、`/etc`、`/opt`、`/srv`、`/mnt`、`/media`。各目录的写入类别见 P2。 |
| macOS 参照 | Signed System Volume：`/System`、`/usr`、`/bin` 密封只读。 |
| 模块章节 | §13 文件系统、§15.2 隔离、§20 更新事务。 |
| 当前源码 | **已落实普通写入入口的系统只读规则**：`filesystem/policy.rs` 的统一分类门覆盖创建、替换、追加、文件删除、目录删除，root 身份也不能绕过。配置表在 `config.rs`；更新事务入口尚未实现。 |
| 实现位置 | `filesystem/policy.rs` / `backend.rs` / `types.rs`。错误为 `ReadOnlySystemPath`，与根/布局目录自身的 `ProtectedPath` 分开。 |
| 验收 | `mkdir /usr/x`、`touch /bin/y`、`touch /usr/lib/z` 全部拒绝并报系统目录只读；`mkdir /home/x`、`touch /tmp/y` 成功。对照实验：临时摘掉白名单检查，上述命令必须成功，证明检查是必要的。 |

### P2 每个可写目录有明确的所有者和生命周期

| 目录 | 所有者 | 类别 | 删除条件 |
|---|---|---|---|
| `/home/<user>` | 该用户 | 用户数据 | 只有用户自己删；系统永不自动删 |
| `/root` | root | 用户数据 | 同上 |
| `/tmp` | 写入它的任务 | 临时 | **每次启动清空**；任务退出后其临时文件可删 |
| `/var/cache` | 写入它的应用 | 缓存 | 系统可在任何时候清空，应用必须能在缓存丢失后正常工作 |
| `/var/log` | 系统日志模块 | 日志 | 按大小/条数轮转，旧日志自动删除，上限写在配置 |
| `/var/run` 或 `/run` | 运行中的任务 | 运行时状态 | 每次启动清空；任务退出时自己删 |
| `/etc` | 系统配置模块 | 配置 | 只有配置命令能写；应用不直接写 |
| `/opt/<app>` | 该应用 | 应用自包含目录 | 删除目录 = 卸载应用，不留任何其他痕迹 |

规则：

- 一个任务只能写自己所有者范围内的目录。应用写 `/home/<user>/.config` 之类的位置必须经过系统接口登记，不能裸写。
- 没有所有者的写入请求被拒绝。宿主原型阶段"所有者"就是当前命令，用户模块落地后变成用户 + 任务。
- "缓存"的定义：删了之后程序仍然正确只是变慢。不满足这个定义的东西不许放进 `/var/cache`。
- **macOS 参照**：`~/Library/Caches` 由系统在存储紧张时清空；`/private/tmp` 启动清理；`launchd` 维护 `periodic` 清理日志。
- **模块章节**：§13、§18.2 日志/配置、§21 日志轮转。
- **当前源码**：`config.rs` 已有 `DirectoryPolicy`、`WriteClass` 和集中前缀分类表，普通写入拒绝未分类路径。旧 `directories` 保持布局兼容。用户/任务/应用的持久登记与各类别完整生命周期仍未实现，不能把分类完成写成 P2 全部完成。`tasks.rs` 的任务仍没有所有者字段。
- **日志增量（2026-11-08）**：新建受管日志实现分代限额、轮转、提交前缀校验及有归属恢复；日志预算集中在 `config.rs`，调用接口在 `logging.rs`、实现协议在 `filesystem/log_store.rs`。普通修改受管日志被拒绝，历史无归属日志保留只读，不自动认领。仅日志生命周期子项完成，用户/任务/应用普通对象归属、缓存治理及全量临时数据生命周期仍待实现。普通追加为 HostBuffered，不能据此宣称断电持久化。
- **实现位置**：`config.rs` 把 `directories: &[&str]` 改成带类别的结构（如 `(path, WriteClass)`），`WriteClass` 枚举 `SystemReadOnly / UserData / Temporary / Cache / Log / RuntimeState / Configuration / Application`；文件系统写接口按类别检查。
- **验收**：启动两次，第一次在 `/tmp` 创建文件，第二次启动后 `ls /tmp` 为空；`/home` 下的文件两次启动都在。

### P3 临时文件不许留在用户目录

| 项目 | 内容 |
|---|---|
| 规则 | 任何中间产物（暂存写入、下载中的文件、编译中间件）只能在 `/tmp` 或 `/var/cache` 下创建，不能和目标文件放在同一目录。 |
| 为什么 | 暂存文件放在目标旁边，进程崩溃后它就成了用户目录里一个没人认领的文件——这正是"隐形垃圾"。 |
| 当前源码 | **本轮已选择并实现方案 (a)**：`filesystem/transaction.rs` 将暂存放在带归属标记的 `/tmp/.elara-transactions/`，普通虚拟路径保留此组件；不再在用户目标文件旁边写 `.elara-staged-*`。 |
| 当前选择 | 暂存 payload 写入并同步后，通过能力目录句柄进行原子 rename；跨设备或宿主不支持时明确失败，旧文件不变，绝不退回复制覆盖。提交凭据分别报告目录同步和跟进清理状态。 |
| 恢复规则 | `filesystem/recovery.rs` 只回滚本系统标记的事务残留，不重放目标文件、不跟随链接、不扫普通用户 `/tmp` 文件。未知或错误归属内容保留，未标记事务目录报错。启动与写入共享同一文件锁。历史同目录暂存文件不自动删除。 |
| 验收 | `tests/filesystem/transaction.rs` / `recovery.rs` / `boundary.rs` 覆盖成功提交、部分暂存失败、模拟跨设备拒绝、并发替换与恢复、归属识别、初始化实际调用恢复，以及路径检查后父目录替换的能力边界。真实跨卷与断电未测，不外推。 |

### P4 应用自包含

| 项目 | 内容 |
|---|---|
| 规则 | 一个应用 = `/opt/<name>/` 一个目录，程序、资源、依赖全在里面。应用的用户数据在 `/home/<user>/<name>/` 或系统登记过的位置。卸载 = 删除 `/opt/<name>/`，再按登记表删除它的用户数据和缓存。 |
| 禁止的事 | 安装器往 `/usr/lib` 放共享库；应用往 `/etc` 写自己的配置；应用在多个目录散落文件。 |
| 登记表 | `/var/lib/elara/apps/<name>` 记录该应用登记过的所有写入位置；没登记的位置写入被拒绝。这张表就是"系统知道每个字节属于谁"的实现。 |
| macOS 参照 | `.app` bundle 自包含；删除 = 拖进废纸篓；沙箱容器 `~/Library/Containers/<bundle-id>`。 |
| 模块章节 | §20 软件包格式、包数据库。 |
| 当前源码 | 没有应用概念，`/opt` 只是空目录。目前可不实现，但 P1/P2 的白名单设计必须给 `/opt/<name>` 和登记表留位置。 |
| 验收 | 安装一个示例应用后 `find /` 的新增条目只在 `/opt/<name>` 和登记表列出的位置；卸载后 `find /` 与安装前一致。 |

### P5 任务有优先级类别，前台永远优先

| 项目 | 内容 |
|---|---|
| 规则 | 每个任务有一个 QoS 类别：`Interactive`（用户正在等它的输出）> `UserInitiated`（用户发起、明确在等）> `Default` > `Utility`（长时间后台工作）> `Background`（用户看不见的维护）。调度和资源限制按类别，不按数字优先级。 |
| 命令行系统的对应 | 前台命令 = `Interactive`；`sleep N bg` 这类 = `Utility`；日志轮转、`/tmp` 清扫 = `Background`。将来的管道、脚本继承发起者的类别。 |
| 低类别任务的约束 | `Background` 任务不能抢 `Interactive` 的 I/O；内存紧张时先杀 `Background`，再 `Utility`，`Interactive` 最后。这就是 macOS Jetsam 的顺序。 |
| 优先级继承 | 高类别任务等低类别任务持有的资源时，低的临时提升到高。内核阶段实现；宿主原型只定义枚举。 |
| macOS 参照 | XNU QoS 等级、App Nap、Jetsam。 |
| 模块章节 | §7.2 调度策略与优先级继承、§8.3 OOM 处置、§16.1 资源治理。 |
| 当前源码 | `tasks.rs` 的 `Task` 只有 `id/command/state/completion`，没有类别字段；`TaskTable` 容量 16 是硬上限，满了直接拒绝，没有"先杀低类别"的策略。 |
| 实现位置 | `tasks.rs` 增加 `QosClass` 枚举和 `Task.qos` 字段，`spawn_*` 必须显式传类别，不给默认值；`ps` 输出显示类别；表满时拒绝的是低类别而不是先来后到。 |
| 验收 | `ps` 显示类别列；表满时 `sleep 5 bg`（Utility）被拒绝但前台命令仍能执行；对照实验：去掉类别判断，表满时前台命令也被拒绝。 |

### P6 配置是文件，不是数据库；变更是事务

| 项目 | 内容 |
|---|---|
| 规则 | 所有配置都是 `/etc` 下的纯文本文件，一个主题一个文件，`cat` 就能看全。没有中央注册表，没有二进制配置库。 |
| 事务 | 系统目录（P1）和 `/etc` 的变更以事务进行：先写新版本到暂存位置，验证通过后原子切换，失败则旧版本不动。事务记录在 `/var/log`。 |
| 禁止的事 | 应用自己解析和改写 `/etc` 的文件；一份配置散在多个文件；配置文件里出现宿主路径。 |
| macOS 参照 | plist 文件 + `defaults` 命令；APFS 快照保证系统更新可回滚。 |
| 模块章节 | §18.2 配置管理、§20 更新事务与回滚。 |
| 当前源码 | `users.rs` 正在做 `/etc/passwd` 式账号文件，方向符合本原则；`write_file` 已有暂存 + 原子替换的雏形。 |
| 验收 | 配置写入中途制造失败（比如暂存文件写到一半），旧配置内容完整不变。 |

### P7 不提供清理工具；需要清理即是缺陷

| 项目 | 内容 |
|---|---|
| 规则 | ElaraOS 不提供"磁盘清理""优化""修复注册表"类命令。`/tmp`、`/run` 的启动清扫和 `/var/log` 轮转是 P2 定义的生命周期，不是清理工具。 |
| 审查规则 | 任何会话发现有文件"不知道是谁写的、不知道能不能删"，这是一个缺陷，要追溯写入源头并按 P1–P4 修正，而不是增加一条删除逻辑。 |
| 可观测性 | 提供 `du`、`find` 之类只读命令让用户看到磁盘上有什么（命令账本 §4.4）；提供应用登记表查询让用户知道每个文件属于谁。看得见就不隐形。 |
| 模块章节 | §21 可观测性。 |
| 验收 | README 和命令账本中不出现任何清理类命令；代码审查时以本条拒绝此类提交。 |

## 4. 内存与响应（内核阶段）

以下机制依赖自有内核，宿主原型阶段不能实现，只在这里固定设计意图，避免将来内核设计时遗漏：

| 机制 | 意图 | 模块章节 | 宿主原型能做的 |
|---|---|---|---|
| 内存压缩优先于换页 | 不活跃页先压缩，压缩后仍不够才考虑写存储 | §8.3 回收策略 | 无 |
| 按 QoS 类别处置内存不足 | 先终止 `Background`，再 `Utility`，`Interactive` 最后；**明确不做**"整机 swap 到无响应" | §8.3 OOM 处置 | 任务类别枚举（P5） |
| 后台任务节流 | 不在前台的任务 CPU 配额与定时器频率降低 | §7.2、§16.1 | 任务类别枚举（P5） |
| 固定节拍输出 | 终端输出按固定周期刷新，慢任务的输出不阻塞前台命令的回显 | §19.1 TTY、§12.1 背压 | 命令行输出缓冲策略 |
| 优先级继承 | 防止低类别任务持锁阻塞高类别 | §7.2 | 无 |

**明确不采用的**：垃圾回收式的内存管理。ElaraOS 的内核与系统程序用 Rust 所有权模型，对象生命周期在编译期确定，不存在 GC 暂停；这对应 macOS 平台选择 ARC 而非 GC 的决定。
